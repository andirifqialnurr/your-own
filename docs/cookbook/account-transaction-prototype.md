## 1. Actual implementation boundary

Two independent **Node/Nest service processes**, each with its own real generated Prisma client/pool, exercise the unmodified auth **0.1.1** module/services against one scratch PostgreSQL database. A third fresh service process replaces one instance during each suite. Private test IPC carries synthetic requests/results; **no new HTTP controller, BFF, browser or native protocol is tested here**. Test-only seeding/signing/failure/clock controls are not production APIs.

Unlike the preceding HTTP phase, user/password/lifecycle/staff revision and logical grant state are **durable synthetic SQL records**, not memory users. Four new scratch tables (`auth_accounts`, `auth_grants`, `auth_audits`, `auth_outbox`) extend the seven previous auth tables; refresh families gain a unique grant binding. The outbox's audit FK is genuinely **DEFERRABLE INITIALLY DEFERRED**, checked in the PostgreSQL catalog. This is an external schema/migration, not `apps/api/prisma` or a production design adoption.

The owned context uses a correctly typed **`Prisma.TransactionClient`** and account-row `FOR UPDATE`, explicit ownership/lifetime checks and READ COMMITTED transactions. Participating reset/store handlers use that same transaction; no cast of a transaction client to a root client, hidden nested transaction or global write fallback. Password verification happens before grant creation, then its original hash/generation is rechecked under the account lock. Reset uses the real library with `signIn:false`; only a non-authorizing, library-compatible SHA-256/base64url lookup routes its account lock. Library redemption/fingerprint/password/MFA crypto is unmodified.

A separate explicit email-token issuance entry can open its own coordinated transaction for the library's deferred reset request; memory mail capture happens after that save commits. It is **not durable mail scheduling/delivery**. Memory retains only test keys, mail, clock/hooks/metrics; actual credential/grant state is in SQL. A shared parent supplies ephemeral keys across process reopen, not production secret custody.

Native-style JWTs carry server-generated fixture grant/generation/realm bindings. Signature verification is followed by one authoritative account/grant/family read. Cookie-token lookup checks equivalent bound state. **The added owned live gate** denies revoked access: the bare library's stateless JWT behavior has not changed. Private signing-oracle commands deliberately mint malformed signed claims for tests; no public signing route exists.

## 2. Verified cases

Final suite: **30 Node entries twice** (29 subtests + one parent), zero failure/skip, **26.177 s / 26.141 s**.

| Area | Actual observation |
|---|---|
| Durable composition | Independent Nest processes share SQL account/hash/generation and bound JWT/session state. Write without an active owned unit of work fails without changing rows. |
| Reset rollback | Ten failure boundaries: token consumption, session/grant revocation, family revocation, hash/generation update, sibling reset deletion, verification, completed library service, audit, outbox and COMMIT. Fresh clients compare complete account/grant/session/refresh-token/family/reset-token/audit/outbox snapshots; old coherent state survives and no successful capability response escapes. |
| Real COMMIT rejection | Inject an orphan audit reference into the deferred-FK outbox. PostgreSQL **23503** occurs **after the transaction callback returned**, not just an application throw before commit; snapshot rolls back. The library's reset diagnostic still increments, explicitly proving it is not durable committed audit. |
| Successful reset | Replacement password works; old password fails. Old JWT is still cryptographically valid but live access is denied in both processes; opaque session access also fails. The reset token cannot be reused. Required audit/outbox reference pair commits together. |
| Response ordering | Hold issuance inside the transaction after the real token pair exists. No IPC response is sent and a fresh client sees no uncommitted grant. Release/commit, then the returned pair authorizes. This is service-result buffering, not browser cookie/network-delivery proof. |
| Late password verification | Hold another process after real old-password verification, commit reset, then release it. Rechecking the original hash/generation prevents issuance with the newer generation. |
| Device logout / refresh | Hold refresh before its transaction; commit stable-grant logout, then release. The held credential cannot renew; a different grant/device remains authorized. |
| Competing resets | Independent coordinator holds the account row; **two distinct runtime backends** are observed lock-waiting before release. Two previously valid reset links yield exactly one accepted transition and generation increment. |
| Generation / grant cutoffs | Same controlled clock/issuance time: generation cutoff rejects an otherwise valid JWT. Revoking just the logical grant also suffices; the model does not rely only on cleanup of rotating digests. |
| Binding validation | Missing/malformed/cross-owner/cross-realm/wrong-generation/unsafe-number or noncanonical generation claims and hostile issuer fail even with the test signing key. Signing inputs on ordinary issuance are server-owned, not arbitrary request claims. |
| Refresh denial semantics | Real token reuse revokes family **and bound grant**, commits the intended invalid-token outcome and denies old access. It is not rolled back merely because the client gets denial. |
| Process reopen | Close one Nest process/pool and start a fresh process with the same ephemeral parent-held keys; existing SQL account/credential state authorizes, then revokes consistently across instances. No memory-user reseed occurs. |
| Lifecycle / authority failure | Suspended/Deleting/Deleted state denies still-signed credentials and password sign-in. Actual runtime SELECT denial on authority rows returns safe unavailable with PostgreSQL **42501**; after grant restoration the live credential works. No cached-positive/signature-only fallback. Not a network outage/restore proof. |
| MFA / staff | Incorrect real TOTP returns a committed denial with an actual persisted failure count. Valid real TOTP issues trusted assurance. A completion held after verification holds the account lock: logout on another process is observed waiting, then commits after completion and denies the grant. Staff removal/regrant changes revision, so earlier fresh TOTP context does not revive. |

The two explicit barriers observe **2** waiting backends for reset contention and **1** for step-up/logout, in each positive run (and again in controls). Other gated interleavings use private IPC hooks and are not mislabeled as explicit SQL barriers. Clock values are controlled test time, not validated production clock/skew policy.

All three service instances' metrics are captured, including the one closed before reopen: **76 unit-of-work samples per positive suite**, observed maxima **650.090 ms / 538.837 ms**, below the fixture's 10-second transaction timeout/12-second outer assertion. Real library-default scrypt is used, serial fixture hashing with no cost reduction. These small local samples are **not** production latency/capacity/lock-duration budgets or exhaustive timeout evidence; hashing still occurs inside the reset transaction.
